{% comment %}The arrange bar, in a SLOT that always exists. The bar itself appears and disappears with the list's type and its sections, so it cannot be its own out-of-band target: htmx matches OOB content by id against an element already in the document, and going from Collection to Ranked means the bar is not there to match. The empty slot is always there, so the swap always lands. VISIBILITY IS THE SERVER'S ANSWER NOW. An earlier version computed it in JS from the currently SELECTED type radio, because saving a type change meant a full page reload and the bar would otherwise have sat there offering to reorder a list the hunter had just said was a shelf. Saving now refreshes this slot instead, so the bar simply reflects what the list IS -- which is also more honest while the radio is changed but unsaved, since the list really is still ranked until you save. The JS still hides it while the editor is closed. That is the deliberate-entry half: the handles used to be live whenever a ranked list was viewed by its owner, which made rearranging something you could do by accident. ONE BAR, TWO CAPABILITIES, and they are not the same one. `can_arrange` is "cards can be dragged at all", which on a sectioned list means FILING one under a header; `can_reorder` is the stricter "a drop position means something", true only at the real sequence. A sectioned Collection has the first and not the second, which is why the toggle inside is gated separately from the bar around it. {% endcomment %}
